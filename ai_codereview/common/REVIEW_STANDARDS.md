# 團隊 Code Review 標準

> 兩種模式（json / mcp）共用這份檔案，改這裡就同時生效。
> 個別 repo 若有特殊規則，寫在該 repo 的 `docs/REVIEW.md`，agent 會一併讀取；兩者衝突時以 repo 的為準。

## 嚴重度定義（決定是否在程式行上留言）

| 等級 | 定義 | 範例 |
|---|---|---|
| critical | 合併後幾乎確定造成事故、資料損毀或資安漏洞 | SQL injection、權限檢查遺漏、會刪錯資料的邏輯 |
| high | 很可能造成 bug 或違反團隊硬性規定 | 未處理的錯誤路徑、race condition、controller 直接存取 DB |
| medium | 有實際風險但影響有限，或明顯的維護性問題 | 缺少 timeout、新 API 沒有測試、與 MR 目的無關的大範圍異動 |
| low | 小建議，可做可不做 | 命名、可讀性、可簡化的寫法 |

預設只有 **medium 以上**會發行內留言，low 只列在總結的摺疊區。

## 必查項目

1. **正確性**：邏輯錯誤、邊界條件（null / 空集合 / 0 / 時區）、錯誤處理是否吞掉例外
2. **安全**：注入、權限檢查、機密資訊寫進程式碼或 log、不安全的反序列化
3. **架構規則**
   - controller 層不得直接存取 DB，須經 service 層
   - 所有外部 API 呼叫必須設定 timeout 並處理失敗
   - 不得在 log 中輸出個資、token、密碼
4. **測試**：新增或修改的公開 API／商業邏輯必須有對應測試
5. **變更範圍（AI 開發特別注意）**：與 MR 標題／描述目的無關的檔案異動、順手重構、大量格式化——列為 `scope` 類別，嚴重度 medium
6. **資料庫**：migration 是否可回滾、是否對大表加了會鎖表的操作

## 不要回報

- 純格式、排版、import 順序（交給 formatter / linter）
- 個人偏好的寫法差異
- 沒有具體證據的「可能有問題」——不確定就不要報
- 自動產生的檔案、lock 檔

## 語氣

- 使用繁體中文
- 直接說明問題與原因，並給出具體修改方向；能給修正後的程式碼就給
